## 0. Headline corrections (read these first)

1. **Do not run v0.34.2 if you pull from hf.co** — it blocks the hf.co → CDN redirect ("blocked redirect to a different host"; issue #18526, regression from #18512). Fixed in v0.34.3 by PR #18533 (merged 2026-09-19). Source: https://github.com/ollama/ollama/pull/18533 , https://api.github.com/repos/ollama/ollama/releases/tags/v0.34.3 ("Includes a fix for HuggingFace model pulls").
2. **Integrated GPUs are dropped by default.** `discover/runner.go` (v0.34.2) drops every `device.Integrated` GPU unless `OLLAMA_IGPU_ENABLE` is explicitly set, or the device is CUDA, or it is ROCm with GFX target in `defaultIntegratedROCmGFXTargets = {"gfx1151"}` (Radeon 8060S / Ryzen AI Max+ 395 only). Log line: `dropping integrated GPU; to enable, set OLLAMA_IGPU_ENABLE=1`. Without `OLLAMA_IGPU_ENABLE=1` the 780M is never used (CPU-only, info-level log, no error). Source: https://raw.githubusercontent.com/ollama/ollama/v0.34.2/discover/runner.go (lines 20-50 and `filterIntegratedGPUs`), https://raw.githubusercontent.com/ollama/ollama/v0.34.2/envconfig/config.go (`EnableIntegratedGPU = BoolWithDefault("OLLAMA_IGPU_ENABLE")`, description "Enable integrated GPUs").
3. **gfx1103 (780M) is not a supported ROCm target in Ollama's build**; the supported LLVM targets are gfx908, gfx90a, gfx942, gfx950, gfx1030, gfx1100, gfx1101, gfx1102, gfx1150, gfx1151, gfx1200, gfx1201. The docs' override example is `HSA_OVERRIDE_GFX_VERSION="10.3.0"` (RX 5400); **`11.0.2` appears nowhere in the docs**. Community reports use `11.0.0` (issues #15482, #3189) and llama.cpp issue #20839 (same 7940HS) shows the HIP backend crashing under that override. Vulkan is the documented, default-on path for "additional GPU support".
4. **Ollama has run GGUF models through llama.cpp's `llama-server` since v0.30.0 (2026-05-13)**; PR #16031 (merged 2026-05-29) removed the CGO engines. GPU offload is therefore llama-server's `--fit` auto-fit, not an Ollama estimate; Ollama only passes `-ngl` when you set `num_gpu`.
5. **Qwen3.8-27B is a hybrid Gated-DeltaNet model: only 16 of 64 layers have a KV cache.** The naive "2 × 64 layers" KV formula overstates KV memory 4×. Correct f16 KV cost = **64 KiB/token** (1 GiB at 16k, 2 GiB at 32k); q8_0 = 34 KiB/token.
6. **`/no_think` is not documented for Qwen3.8.** Neither the model card nor `chat_template.jinja` contains `/no_think` or `/think`. Thinking is disabled via `chat_template_kwargs: {"enable_thinking": false}` (template then emits `<think>\n\n</think>\n\n`). Ollama's `think:false` maps to exactly that for Jinja-rendered models, and its Go renderer for `qwen3.8` accepts `[false, "low", "medium", "xhigh"]` (default `xhigh`).
7. **The hf.co pull gives you an HF-generated 410-byte Go template that hard-codes non-thinking mode and the "xhigh" preamble, no tool support**, plus a params layer of stop tokens only. The official `qwen3.8:27b-q4_K_M` library model instead uses Ollama's built-in `qwen3.8` renderer (no template layer) with thinking-mode sampling defaults.
8. **Default context on this machine will be 4096**, because `OLLAMA_CONTEXT_LENGTH` defaults to 0 = VRAM-tiered: ≥47 GiB → 262144, ≥23 GiB → 32768, else 4096 (`server/routes.go`). The FAQ sentence "By default, Ollama uses a context window size of 4096 tokens" and modelfile.mdx "num_ctx (Default: 2048)" are both stale simplifications.
9. **Known open regression on exactly this hardware**: issue #17748 (opened 2026-08-14, open) — Radeon 780M + Vulkan, Ollama ≥ 0.32.10, models ≥ 18 GB crash with `radv/amdgpu: Not enough memory for command submission` / `vk::Queue::submit: ErrorDeviceLost`; ≤ 6 GB models fine; workaround `OLLAMA_VULKAN=0` + `OLLAMA_IGPU_ENABLE=0` (CPU). The 27B UD-Q4_K_M + mmproj is in the affected size class. Treat GPU offload on this box as a staged experiment.

### B4. KV-cache and total memory (computed; re-checkable)

Inputs (all from B1.3 / B1.6 / llama.cpp source):
- Layers with a KV cache: **16** (config `layer_types` has 16 `full_attention`; llama.cpp `src/models/qwen35.cpp`: `is_recr_impl[i] = (i < n_layer()) && ((i + 1) % full_attn_interval != 0)` with `full_attn_interval` read from `qwen35.full_attention_interval = 4`; `llama_memory_hybrid` gives the attention KV cache only to layers with `!hparams.is_recr(il)`).
- `num_key_value_heads` = 4, `head_dim` (key_length = value_length) = 256 → per layer per token K+V = 2 × 4 × 256 = 2,048 elements.
- Bytes/element: f16 = 2; q8_0 = 34/32 = 1.0625 (`block_q8_0 = ggml_half d + int8_t qs[32]`, `QK8_0 32`); q4_0 = 18/32 = 0.5625 (`block_q4_0 = ggml_half d + uint8_t qs[16]`). Source: https://raw.githubusercontent.com/ggml-org/llama.cpp/master/ggml/src/ggml-common.h

Formula: `KV_bytes/token = 2 × L_attn × n_kv_heads × head_dim × bytes_per_elem = 2 × 16 × 4 × 256 × b = 32,768 × b`

| Cache type | per token | 16,384 tokens | 32,768 tokens |
|---|---|---|---|
| f16 (default) | 65,536 B = 64 KiB | 1,073,741,824 B = **1.00 GiB** (1.07 GB) | **2.00 GiB** (2.15 GB) |
| q8_0 | 34,816 B = 34 KiB | 570,425,344 B = **0.53 GiB** (0.57 GB) | **1.06 GiB** (1.14 GB) |
| q4_0 | 18,432 B = 18 KiB | 0.28 GiB | 0.56 GiB |

(If you had used all 64 layers, you would get 256 KiB/token → 4 GiB at 16k f16 — wrong by 4×.)

Recurrent (Gated DeltaNet) state — constant per sequence slot, independent of context, f32 (`llama-model.cpp`: `/* recurrent_type_r */ GGML_TYPE_F32, /* recurrent_type_s */ GGML_TYPE_F32`):
- `n_embd_s = ssm_d_state × ssm_d_inner = 128 × 6144 = 786,432` elems × 4 B = 3 MiB per layer × 48 layers = **144 MiB**
- `n_embd_r = (ssm_d_conv − 1) × (ssm_d_inner + 2 × ssm_n_group × ssm_d_state) = 3 × (6144 + 2×16×128) = 30,720` elems × 4 B = 120 KiB per layer × 48 = **5.6 MiB**
- Total ≈ **0.15 GiB per parallel slot** (× `OLLAMA_NUM_PARALLEL`). Source: https://raw.githubusercontent.com/ggml-org/llama.cpp/master/src/llama-hparams.cpp (`n_embd_r()`, `n_embd_s()` fallback branch; assumes qwen35 does not set `wkv_head_size`/`n_embd_head_kda`/`n_embd_head_la` — consistent with the GGUF keys above but not independently verified).

## Unverifiable items and how to resolve them

1. Which Ollama release flipped Vulkan to default-on — no release note; resolve by `journalctl -u ollama` showing Vulkan devices without `OLLAMA_VULKAN=1`.
2. Memory the 780M exposes under Vulkan on this box (GTT) — read the `inference compute` log line at startup; compare with `cat /sys/class/drm/card*/device/mem_info_gtt_total`.
3. Whether `think:false`/`true` is accepted for the hf.co-pulled model with the HF Go template — run `ollama show hf.co/unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_M` (v0.34.3 prints thinking controls) and one `/api/chat` call with `think:false`.
4. Whether `RENDERER qwen3.8` / `PARSER qwen3.8` in a Modelfile attach the built-in renderer to the HF GGUF — parser accepts the words; behaviour untested and undocumented.
5. Compute-buffer size for this architecture at 16k/32k — read llama-server's memory log lines (or `LLAMA_ARG_FIT_ESTIMATE`) on first load.
6. Minimum llama.cpp b-release for Qwen3.8 GGUFs — not published; Ollama v0.32.12+ is the practical floor.
7. Fedora package name for the RADV Vulkan ICD — not in Ollama docs; check `vulkaninfo --summary`.
